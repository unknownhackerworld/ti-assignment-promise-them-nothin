  - The CTO wants it auditable and explainable in one paragraph. "We store each
  request timestamp in a sorted set; the count of entries within the trailing 60

  adjacent fixed windows" is harder to defend to an enterprise security reviewer
  who asks "so what's my exact count right now?"

  expire old entries, ZCARD to count. Atomic with a pipeline or Lua script.

  3. Redis Failure Mode

  The CTO said:

  ▎ "I would rather reject a few extra legitimate requests than let someone blow
  ▎ past quota because nodes disagreed."

  This rules out fail open entirely. If Redis dies and you allow all traffic,
  you've violated the core invariant.

  But full fail closed (reject everything) is a complete outage — that's
  arguably worse for the business than a quota violation.

  The pragmatic middle ground: degrade to a conservative per-node local limit.

  fallback_rpm = configured_rpm / num_nodes

  So if Northwind's limit is 300 RPM and there are 3 nodes, each node
  independently allows 100 RPM when Redis is unreachable. This means:

  - If traffic is evenly distributed: customer gets their full 300 RPM (100
  × 3). No degradation.
  - If traffic is skewed to one node: customer gets at most 100 RPM from that
  node. They're under-limited — which is exactly the error direction the CTO
  accepts.
  - Worst case: customer loses ~2/3 of their throughput during a Redis outage.
  That's painful but recoverable, and you never exceed quota.

  You'd also want:
  - A health check that detects Redis unavailability quickly (not on the request
  hot path)
  - Metrics/alerts so ops knows the system is degraded
  - The local fallback counter resets when Redis returns (don't carry stale
  local state forward)

  ---
  4. Clock Skew at the Batch Window Boundary

  This is a real class of bug. If node A's clock is 200ms ahead of node B, then
  at 02:00:00.000 UTC:
  - Node A thinks it's 02:00:00.200 → applies elevated limit
  - Node B thinks it's 01:59:59.800 → still on base limit → rejects Northwind's
  burst traffic

  For a 2-minute window this might only cause a handful of 429s, but that's
  enough to trigger Northwind's aggressive retry logic and amplify the problem.

  Solution: Don't use node-local clocks for schedule evaluation.

  Since you're already using Redis as the coordination layer, use Redis as the 
  authoritative clock:

  -- In your Lua rate-limit script:
  local now = redis.call('TIME')  -- returns [seconds, microseconds]

  All three nodes ask Redis "what time is it?" as part of the same atomic
  rate-limit operation. Since there's one Redis, there's one clock, and the
  schedule transition happens atomically for all nodes.

  Bonus: this also means you don't need NTP synchronization between app nodes to
  be perfect — the app nodes' clocks become irrelevant to the rate-limiting
  decision.

  If Redis is unavailable (fallback mode from question 3): you're already on the
  conservative per-node local limit, which doesn't use schedule overrides
  anyway — you'd fall back to base_rpm / num_nodes. Northwind might see some
  429s during a Redis outage that overlaps their batch window, but that's an
  infrastructure failure, not a design flaw.

  4. On Lua in Redis — Absolutely Yes

  Your instinct is correct and it's the right call for three reasons:

  Atomicity without round-trips. The rate-limit decision requires multiple
  operations that must be atomic:
  1. Get current time (TIME)
  2. Remove expired entries (ZREMRANGEBYSCORE)
  3. Count remaining (ZCARD)
  4. Conditionally add new entry (ZADD)
  5. Set TTL (EXPIRE)

  Without Lua, you'd need WATCH/MULTI (optimistic locking — retries under
  contention) or multiple round-trips (race conditions between nodes). With Lua,
  Redis executes all of this as a single atomic operation — no other command
  can interleave. This is exactly the guarantee you need when 3 nodes are
  racing.

  Single clock source. redis.call('TIME') inside the Lua script means all nodes
  use Redis's clock — solving the clock-skew problem from earlier in one stroke.

  Auditability. The entire rate-limit algorithm lives in one ~20 line Lua
  script. An enterprise security reviewer can read one file and understand the
  complete counting semantics. No distributed state machine spread across
  application code.

  The script would look roughly like:

  -- KEYS[1] = rate limit key (e.g., "ratelimit:{customer_id}")
  -- ARGV[1] = window size in microseconds
  -- ARGV[2] = max requests (effective RPM for current schedule)

  local now = redis.call('TIME')
  local now_us = tonumber(now[1]) * 1000000 + tonumber(now[2])
  local window_start = now_us - tonumber(ARGV[1])

  -- Purge expired entries
  redis.call('ZREMRANGEBYSCORE', KEYS[1], '-inf', window_start)

  -- Count current requests in window
  local count = redis.call('ZCARD', KEYS[1])

  if count >= tonumber(ARGV[2]) then
      return {0, count, now_us}  -- REJECTED
  end

  -- Admit request
  redis.call('ZADD', KEYS[1], now_us, now_us .. ':' .. math.random(1000000))
  redis.call('PEXPIRE', KEYS[1], math.ceil(tonumber(ARGV[1]) / 1000))

  return {1, count + 1, now_us}  -- ALLOWED

  Returns: [allowed (0/1), current_count, timestamp] — everything the app needs
  to build the 429 response with Retry-After header and everything the audit log
  needs.

● You're right on both counts.

  On determinism: Modern Redis (5.0+) uses effects-based replication by default,
  so math.random() technically works. But it's still a smell — if someone
  configures script replication, or you need to debug by replaying scripts,
  non-determinism bites you silently.

  On collisions: This is the real bug. At 1200 RPM (20 req/sec), multiple
  requests landing in the same microsecond is not unlikely. Birthday paradox
